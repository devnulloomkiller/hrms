# Build HRMS on ASP.NET Core with Entity Framework Core

## Context and Problem Statement

HRMS — информационная система кадрового учёта: вакансии, резюме, собеседования. Это учебный проект с фиксированными требованиями: ASP.NET-решение со слоями, модели всех сущностей, `ApplicationDbContext` на `DbContext`, демонстрация CRUD и трёх нетривиальных запросов, аутентификация и авторизация. Стек нужно зафиксировать до создания решения, потому что от него зависят структура папок, выбор NuGet-пакетов и способ реализации доступа к данным.

Ограничения: разработка на macOS (локальная, без IIS), данные демонстрационные, команда из одного человека, сервер БД не задан извне.

## Decision

Строим приложение на **ASP.NET Core 11 в одном решении с послойной структурой проектов** (на машине установлен только .NET SDK 11; net8.0 больше не поддерживается, поэтому берём текущий LTS-мейнстрим), доступ к данным — через **Entity Framework Core** с провайдером **SQLite** для разработки и демонстрации.

Состав решения и слои:

- `Hrms.Domain` — модели сущностей (Vacancy, Resume, Candidate, Interview, …) без зависимостей от инфраструктуры.
- `Hrms.Application` — интерфейсы сервисов и нетривиальные запросы; зависит только от `Hrms.Domain`.
- `Hrms.Infrastructure` — `ApplicationDbContext : DbContext`, конфигурация EF Core, репозитории; зависит от `Hrms.Application` и `Hrms.Domain`.
- `Hrms.Web` — ASP.NET Core MVC: контроллеры, представления, аутентификация и авторизация через ASP.NET Core Identity; точка входа.

NuGet-пакеты: `Microsoft.EntityFrameworkCore.Sqlite` и `Microsoft.EntityFrameworkCore.Design` (миграции) в `Hrms.Infrastructure`, `Microsoft.AspNetCore.Identity.EntityFrameworkCore` — для Identity-сущностей в контексте. Пакет `Microsoft.EntityFrameworkCore.InMemory` не используем: CRUD и запросы должны работать против реального провайдера.

Аутентификация и авторизация — ASP.NET Core Identity с EF Core-хранилищем (AspNetUsers в том же SQLite-файле), роли `Admin` и `HR`; защита контроллеров через `[Authorize]` и role-based атрибуты (`[Authorize(Roles = "HR")]`).

Нетривиальные запросы (например: вакансии с истекающим сроком приёма резюме; все резюме и собеседования кандидата; количество собеседований по вакансиям за период) реализуем методами в `Hrms.Application`, возвращающими готовые DTO через `IQueryable` и проекции — без сырого SQL, чтобы запросы были проверяемыми.

Принимаемые компромиссы: SQLite вместо полноценного сервера БД — теряем параллелизм и полный T-SQL, но получаем нулевую настройку на macOS; четыре проекта вместо одного — больше церемоний для учебного проекта, зато требования «слои» и «NuGet-пакеты» выполнены буквально и каждый слой проверяется отдельно.

Non-goals: реальный сервер БД в production, Docker, фронтенд-фреймворки на клиенте (только Razor + минимальный CSS), миграция данных.

## Alternatives Considered

- **ASP.NET Core + Dapper вместо EF Core**: меньше абстракций и быстрее выборки, но требования курса явно требуют класс `ApplicationDbContext`, наследующий `DbContext`, — Dapper не даёт ни `DbContext`, ни миграций из коробки.
- **PostgreSQL как СУБД (Npgsql.EntityFrameworkCore.PostgreSQL)**: ближе к production и богаче SQL, но требует запущенного сервера на macOS (Docker или локальная установка) ради демонстрационных данных; для учебных CRUD и трёх запросов это неоправданная настройка.
- **Один проект без слоёв**: быстрее старт, но прямым образом нарушает пункт задания «организовать структуру папок для слоёв» и смешивает модели с доступом к данным.
- **Аутентификация на JWT без Identity**: проще для API-варианта, но задание — MVC-приложение с авторизацией по ролям; Identity даёт готовое хранилище пользователей, хеширование паролей и управление ролями без самописного кода.
